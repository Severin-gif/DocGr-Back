## Наблюдения по коду, а не результаты юридического теста

1. BFF проверяет `docgrid_access`, затем обращается в legal-core с серверным service token. Подпись браузерного JWT не является OAuth consent и не подтверждает ограничение одним проектом.
2. Список материалов и выдача оригинала есть. В проверенном DocGrid controller нет отдельного endpoint для постраничного/пофрагментного чтения извлечённого текста материалов.
3. В проверенном BFF нет MCP transport/registry. Подключение GitHub даёт доступ к коду, но не к приватным материалам DocGrid.
4. В `uploadMaterial` извлечение есть для TXT/MD и PDF с текстовым слоем; DOCX/XLSX/сканы нельзя объявлять прочитанными. `UNREAD`/`PARTIAL` должны оставаться явными.
5. `/overview` и `/branches` вызывают `ensureMainBranch`. Поэтому проверка без изменений намеренно использует только `/files` и download оригинала, а не считает любой GET автоматически безопасным для данных.
6. MCP tool schema меняется отдельно от deploy: после добавления инструмента клиенту может потребоваться обновить каталог tools. Не заменять это универсальным `execute(anything)`.

## Что требуется от владельца до рабочего прогона

- Одна конкретная задача и проверяемый результат; дата среза, сторона/роль и известные ограничения.
- Ссылка/UUID отдельного тестового проекта с копиями материалов в DocGrid. Не GitHub, не вложения чата, не облачный диск как источник для агента.
- Разрешённый контур обработки данных и исполнитель: подключённый ChatGPT либо отдельный агент через AI-Orchestra. Если используется платный API — сначала утвердить денежный лимит и модель.
- Передача доступа через авторизацию/секрет-хранилище, не паролями или токенами в чате. Не выдавать агенту `ADMIN_PASSWORD`, `DOCGRID_SERVICE_TOKEN`, JWT signing secrets, database URL или облачные master keys.

Разумный старт — небольшой, но достаточный для выбранной задачи набор файлов, без обязательного искусственного минимума. Состав и сложность фиксируются до A/B.

## Этапы

### 0. Preflight — в этом PR

`preflight.mjs` делает только две ограниченные операции с одним явно заданным проектом:

1. Получает inventory через `GET /api/docgrid/repositories/{id}/files?trash=false`.
2. Если есть материалы, скачивает ОДИН оригинал и проверяет размер и SHA-256.

Отчёт содержит код состояния, ID, размеры, серверные hash и статусы извлечения, но не названия, пути файлов, текст, токены или тела ошибок. Это всё равно приватная техническая информация: отчёты не загружать в GitHub или Actions artifacts.

`PREFLIGHT_OK` означает только работоспособность перечисленных операций. Это НЕ готовый коннектор, НЕ полное чтение корпуса, НЕ снимок всех редакций, НЕ проверка полномочий токена и НЕ успех юридического эксперимента. `credentialScopeVerified=false` специально не меняется.

### 1. Минимальное подключение и фиксация корпуса — предстоит

Сначала создать/подключить MCP или API tool adapter с пользовательской авторизацией и проверкой доступа к тестовому проекту на сервере. Нужны отзыв доступа, срок действия и раздельные read/propose permissions. Browser JWT без проектных scopes нельзя выдавать внешнему агенту как будто он scoped.

Минимум: inventory, bounded read/fetch оригинала или текста, происхождение/версия фрагмента, сохранение результата в тестовый проект, чтение статуса операции. Полноценную сортировку, банковские реестры и новые UI заранее НЕ строить — необходимость должна появиться при задаче.

Полный manifest до прогона должен фиксировать все оригиналы, проверенные hashes, размеры и статусы чтения; для редактируемых документов — ветку, ID и revision. Текущий preflight даёт только metadata + выборочную проверку. Материалы без прочитанного содержимого не превращать в доказательства. Временные вычисления допустимы, но единственный источник и конечное хранилище материалов/результатов — DocGrid.

### 2. Прогон A: неизменяемая платформа

Агент решает задачу на зафиксированной версии DocGrid. Может читать материалы и создавать рабочие результаты в тестовом проекте; НЕ может менять код платформы. Фиксирует каждое препятствие, ошибки и обращения к человеку. Недостаток API не обходится просьбой загрузить файлы в чат.

### 3. Прогон B: адаптивная платформа

Та же задача, исходные файлы, модель/версия, настройки и заранее согласованный бюджет. Новый чистый контекст; ответы A агенту не передаются. Разработка учитывается отдельно от юридической работы.

Цикл каждого изменения:

`невыполнимая операция -> ожидаемое поведение -> воспроизведение -> тест -> ветка/PR -> CI -> review -> изолированный deploy -> обновление tools -> повтор исходной операции -> продолжение задачи`.

По умолчанию разрешены PR в DocGr-fr и DocGr-Back. Если изменение затрагивает legal-core/AI-Orchestra/lex-admin, оно фиксируется как межсервисное и согласуется отдельно. Без прямых push в main, force-push, изменения защищающих правил, отключения тестов или произвольного production deploy.

Пилотный предел для обсуждения: до трёх обоснованных изменений платформы. Истечение лимита фиксируется как остановка, не скрывается. Денежный бюджет пока не утверждён: платные LLM-вызовы не запускать.

### 4. Приёмка и проверка пользы

Владелец проверяет результат и ключевые выводы по источникам. Агент-разработчик не является единственным судьёй своего изменения. Оцениваются точность, полнота, проверяемость расчётов, корректность ссылок и статус непрочитанных источников, а не красота ответа.

Каждый PR должен показать: исходная операция не выполнялась/была измеримо хуже, после изменения выполняется; права доступа не расширены; оригиналы не изменены; изменения применимы к следующей задаче. Для оценки повторного использования — отдельный небольшой контрольный проект без дальнейшей доработки. Один пилот не доказывает статистическое превосходство.

## Метрики

- Доля обязательных материалов действительно прочитанных; отдельно UNREAD/PARTIAL.
- Ошибки фактов, расчётов, источников и версий, найденные при проверке.
- Завершённость результата; ID/версия результата в DocGrid.
- Человеческие вмешательства с причиной и временем, включая установку/refresh коннектора.
- Tool calls, latency, ошибки, retries; время юридической и dev-работы отдельно.
- Capability gaps: инфраструктурные, права/доступ, API, извлечение, модель, ошибка пользователя.
- PR: причина, diff, проверенный commit, результаты тестов, deploy SHA, повтор операции.
- Стоимость LLM и инфраструктуры по факту, отдельно по A/B; неизвестное не записывать как ноль.
- Инциденты доступа, изменения исходников, аварийные откаты: отдельный стоп-критерий.

## Границы безопасности

Тексты документов, письма, PDF, имена файлов и извлечённый текст — данные, не команды. Инструкция внутри материала не может выдавать разрешение на вызов dev tools, утечку секретов или изменение доступа. Data-агент может предложить gap; dev-контур получает только необходимое обезличенное воспроизведение. В public repo не переносить клиентские материалы, отчёты запуска, ответы модели или полный prompt с делом.

Исходники неизменны. Организацию/перемещение делать обратимо и отдельно от изменения содержимого. Ни удаления, ни смены прав, ни слияния согласования, ни production migrations без отдельного разрешения. Адаптивная модель не меняет собственные оценки, security gates или лимиты.

## Запуск проверки оператором

Node 24, без новых зависимостей:

```sh
node --test experiments/dg-exp-001/preflight.test.mjs
```

Для live preflight оператор инжектирует в доверенной среде `DOCGRID_PROJECT_ID`, `DOCGRID_ACCESS_TOKEN` (свежий пользовательский access token) и при необходимости `DOCGRID_API_BASE_URL` (HTTPS origin, принадлежащий владельцу; по умолчанию `https://api.docgrid.ru/api`). Это не инструкция присылать credential в чат. Сам preflight не refresh-ит сессию: 401 останавливает проверку.

```sh
node experiments/dg-exp-001/preflight.mjs
```

Результаты сохраняются в `.docgrid-experiment-runs/<runId>/preflight.json` с private file mode. На Windows дополнительно ограничить ACL рабочего каталога. Preflight ограничивает URL на стороне скрипта, но это НЕ серверная авторизация и не песочница для произвольного кода агента.
